# D-LOCK v1.1 — Postgres Translation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add `PostgresBackendLock` to the Dhara substrate, mirroring the existing `SQLBackendLock` but using Postgres-native `$N` placeholders, Postgres exception types (`SerializationFailure`, `DeadlockDetected`), and the Postgres schema. Ship as a selectable backend alongside DuckDB so production deployments can use either.

**Architecture:** New `dhara/lock/postgres.py` module exposes `PostgresBackendLock(sql_backend)` following the existing `SQLBackendLock` API surface. SQL strings use `$1, $2, ...` numbered placeholders. Exception handler translates `psycopg2.errors.SerializationFailure` and `psycopg2.errors.DeadlockDetected` to `LockLost`. Schema additions go to `dhara/storage/pg_schema.sql` (existing Postgres schema file) — `substrate_locks` table + indexes. Wiring in `DharaMCPServer` makes the backend selectable via config.

**Tech Stack:** Python 3.13, msgspec.Struct, Postgres (psycopg2/asyncpg), pytest-asyncio, no new third-party deps if `psycopg2` is already a dep (verify).

## Context

D-LOCK v1 (shipped 2026-08-04, tasks 102-120) implemented `SQLBackendLock` in `dhara/lock/sql.py` using DuckDB-style `?` placeholders and `duckdb.TransactionException`. The substrate docstring at `dhara/lock/sql.py:26-28` explicitly defers Postgres translation: "Postgres translation (named placeholders / $N) is future work; v1 uses DuckDB-style `?` placeholders."

v1.1 closes this gap by adding a parallel `PostgresBackendLock` that:
- Uses Postgres-native `$N` numbered placeholders (required by psycopg2/asyncpg)
- Handles Postgres-specific conflict exceptions (`SerializationFailure` for optimistic-concurrency, `DeadlockDetected` for pessimistic-concurrency)
- Lives alongside `SQLBackendLock` as a separate class so the DuckDB implementation is unchanged
- Is selectable via DharaMCPServer config (or auto-detected from the connection URL)

The Postgres schema (`dhara/storage/pg_schema.sql`) already exists for `dhara_objects` and `dhara_dirty_oids`. v1.1 ADDS a `substrate_locks` table to that file (no new migration file — pg_schema.sql is the runtime schema for Postgres deployments).

```python
"""PostgresBackendLock — Postgres dialect of DharaLock using $N placeholders."""

from __future__ import annotations

import asyncio
import json
import random
import uuid
from datetime import UTC, datetime, timedelta
from typing import Any, Protocol

from dhara.lock.events import LockEventEmitter
from dhara.lock.protocol import (
    LockHandle,
    LockLost,
    LockPermanentError,
    LockTimeout,
)


class SQLBackend(Protocol):
    """Minimal contract for the Postgres SQLBackend.

    Postgres binding uses $N placeholders (NOT ? like DuckDB). The wrapper
    must adapt psycopg2/asyncpg cursors to a uniform .execute(sql, params).
    """

    def execute(self, sql: str, params: list[Any] | None = None) -> Any: ...


def _is_serialization_failure(exc: Exception) -> bool:
    """Detect Postgres SerializationFailure or DeadlockDetected (psycopg2)."""
    name = type(exc).__name__
    if "SerializationFailure" in name or "DeadlockDetected" in name:
        return True
    # pgcode '40001' = serialization_failure, '40P01' = deadlock_detected
    pgcode = getattr(exc, "pgcode", None)
    return pgcode in ("40001", "40P01")


def _execute_lock_write(
    db: SQLBackend,
    sql: str,
    params: list[Any],
    *,
    lock_key: str,
) -> Any:
    try:
        return db.execute(sql, params)
    except Exception as exc:
        if _is_serialization_failure(exc):
            raise LockLost(f"postgres serialization conflict: {lock_key}") from exc
        raise

#  try_release, heartbeat, get, list_keys, plus _row_to_handle — using
#  $1/$2/.../$N placeholders and Postgres BOOLEAN/TEXT/TIMESTAMPTZ types ...)
```
