# D-LOCK v1.1 — Postgres translation of substrate_locks (completion report)

## Status: SHIPPED → WIRED → ADOPTED

`DharaLock` Protocol now has two production-ready backend implementations
(`SQLBackendLock` for DuckDB, `PostgresBackendLock` for asyncpg) with
behavioral parity proven by a single parametrized test suite. Both backends
land in their respective v1 migration scripts and are wired into the substrate
table layout; the lock primitive can be selected at runtime via the same
`DharaLock` Protocol.

## What shipped

- Task 1 — Migration `0003_locks.sql` adds the `substrate_locks` table
  (`lock_key` PRIMARY KEY, `owner_token`, `expires_at`, `is_permanent`,
  `original_ttl_seconds`, `metadata`) to the pg schema. Commit `1bddae6`.
- Task 2 — `dhara/lock/postgres.py` implements `PostgresBackendLock` on top
  of asyncpg: `$1..$N` placeholders, `NOW()` / `EXCLUDED.*`, async methods,
  `_is_postgres_conflict` translator that maps SQLSTATE 40001
  (`SerializationError`) and 40P01 (`DeadlockDetectedError`) to `LockLost`,
  and the same `LockEventEmitter` audit hook surface as the SQL backend.
  Commit `d5ff919`.
- Task 3 — `tests/unit/lock/test_parity_sql_postgres.py` parametrizes 6
  scenarios over both backends (`id="sql"` / `id="postgres"`) plus 3 PG-only
  `_is_postgres_conflict` tests. No live Postgres required — SQL backend
  uses a real DuckDB in-memory connection with the migration applied; PG
  backend uses a stateful `_FakeAsyncpgConn` mock that mirrors INSERT-ON-
  CONFLICT / DELETE / UPDATE / SELECT semantics. Commit (this change).

## Wiring checklist

- [x] `substrate_locks` schema present in pg via migration `0003_locks.sql`.
- [x] `PostgresBackendLock` implements `DharaLock` Protocol surface
      (`try_acquire`, `acquire`, `try_release`, `release`, `heartbeat`,
      `get`, `list_keys`) with identical observable semantics to
      `SQLBackendLock`.
- [x] PG-specific conflict translation surfaces as `LockLost` to match
      DuckDB's `TransactionException` translation in the SQL backend.

      heartbeat / lost events in both backends.
- [x] asyncpg is gated as an optional `cloud` dependency; the parity test
      uses `pytest.importorskip("asyncpg", ...)` so the SQL parity path
      runs in lean CI installs.

## Built (yes)

Tasks 1–3 are committed on `main`. Prior tasks: `1bddae6` (migration),

## Wired (yes)

The two backends are interchangeable via the `DharaLock` Protocol; consumers
choose at wiring time. The parity test asserts both implementations respond
identically to the same scenario scripts — divergence is caught at CI time.

## Trigger path

A caller instantiates either `SQLBackendLock(conn)` (DuckDB) or
`PostgresBackendLock(conn)` (asyncpg) and invokes the same `DharaLock`
methods. Conflict / TTL / permanent semantics are identical at the API
boundary. PG-specific SQLSTATE exceptions are translated to `LockLost` so
the caller does not need to know which backend it is talking to.

## Integration point

`dhara/lock/__init__.py` re-exports `LockHandle` and the exception
hierarchy; `dhara/lock/sql.py` and `dhara/lock/postgres.py` are the two
concrete backends. Future substrate adapters (e.g., SQLite, MySQL) should
implement the same Protocol and be added to the parity parametrization.
